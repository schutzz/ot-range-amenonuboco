# マニフェストエディタの使い方

> ブラウザで開くだけで使えるマニフェストエディタ（[gui/](../gui/)）の解説です。記法そのものの完全なリファレンスは [マニフェスト記法ガイド](./manifest-schema-guide.md) を参照してください。

## エディタは何をするものか

エディタは**マニフェスト（YAML）を書くための道具**であり、環境を立ち上げる機能そのものは持ちません。

```
エディタで組み立てる  →  YAMLをダウンロード  →  手元で provision → docker compose up
     （ブラウザ）                                        （リポジトリが必要）
```

この分担にしている理由は2つあります。ひとつは、**インストールなしで試せる状態**を保つため。もうひとつは、Amenonuboco の主張が「サイバーレンジをコードとして宣言する（Cyber Range as Code）」である以上、**マニフェストこそが唯一の真実**であり、エディタはそれを隠す装置ではなく書き方を教える装置であるべきだからです。だからエディタの画面では、編集の結果がどのYAMLになるかを常に右ペインに表示しています。

## 起動方法

3通りあります。どれでも同じものが動きます。

| 方法 | 手順 |
|---|---|
| 公開版 | ブラウザで開くだけ（README のリンク） |
| ローカルのファイルを直接開く | `gui/index.html` をブラウザにドラッグ、または `open`/`start` で開く |
| ローカルで配信する | `cd gui && python -m http.server 8000` → `http://localhost:8000` |

外部ライブラリを一切読み込まない自己完結の静的サイトなので、ビルドもインストールも不要です。オフラインでも動きます。

## 作る順序

**後の項目が前の項目に依存します。** 依存先が存在しないと選択肢自体が現れないため、この順序で進めてください。

### 1. セグメントを作る

ネットワークの区画です。「＋ 追加」でセグメントを足し、名前・CIDR・種別を決めます。

- **CIDR** はホスト部を 0 にした形で書きます（`10.1.10.0/24` は可、`10.1.10.5/24` は不可）
- **種別（kind）** は図の色分けと意味付けに使われます。制御系なら `ot-lan`、レイヤ2通信なら `ot-l2`、外部境界なら `wan-edge`、物理セキュリティ網なら `security-lan` など
- 観測（ミラーリング）を使うなら、**種別 `observation` のセグメントを1つ**用意しておきます

セグメント名を変更すると、そのセグメントを参照している資産の接続・観測設定も自動で追従します。削除した場合は、参照していた接続が落ちます。

### 2. 資産を足す

コンテナ1つが資産1つです。名前・ロール・イメージ・接続先セグメントを指定します。

**ロールを選ぶと、その資産に必要な実行属性（`cap_add`・`sysctls`）が自動的に決まります。** 例えば `l3-router` なら IP フォワードが有効になり、`observer` や `structurer` にはパケットキャプチャ権限が付きます。欄の下に「ロール既定 →」として何が付くかを表示しているので、確認しながら選べます。

このとき重要なのが**ゲートウェイ役の資産**です。

> **ゲートウェイには `l3-router` ロールを選び、すべてのセグメントに接続させ、各セグメントで静的IPを指定してください。**
> ゲートウェイはセグメント間の経路を担うだけでなく、**ミラーリングの実行主体**にもなります。全セグメントに接続している唯一の資産だからです。

接続先は「＋ 接続先を追加」で増やせます。IP を空欄にすると動的割当になりますが、**ゲートウェイだけは静的IPが必須**です（後述の警告で指摘されます）。

### 3. ルーティングでゲートウェイを選ぶ

プルダウンから選ぶだけです。**`l3-router` ロールの資産しか候補に出ません**。選ぶと、各資産が自分の接続していないセグメントへ到達するための経路が自動生成されます。

候補が空の場合は、手順2に戻って `l3-router` の資産を作ってください。

### 4. 計装層（ミラーリング）を有効にする

チェックを入れ、**ミラー集約先**のセグメント（手順1で作った `observation` のもの）を選びます。

観測対象は**オプトアウト方式**です。集約先を決めた時点で、**残りの全セグメントが自動的に観測対象になります**。観測から外したいセグメントだけを「exclude」でチェックしてください。

この方式にしているのは、「セグメントを追加したのに観測対象への追加を忘れる」という取りこぼしを構造的に防ぐためです。列挙方式（オプトイン）だと、環境が育つほど観測漏れが起きやすくなります。

図では、各セグメントの枠色と下端バッジが観測状態を示します。**観測外（死角）は最も目立つ色**で描かれます。

### 5. 構造化層を有効にする

チェックを入れ、プロトコルと出力先の Elasticsearch index を登録します（例：`dnp3` → `ot-logs-dnp3-*`）。

1プロトコルにつき専用の tshark プロセスと専用の index が1つ、という対応で配線されます。index の命名は `ot-logs-<protocol>-*` に統一してください。

構造化はミラーされたトラフィックを対象にするため、**計装層が前提**です。構造化だけを有効にすると計装層も自動で有効になります。

## 画面の見方

### 中央：ネットワーク図

編集するたびに描き直されます。セグメントは円周上に自動配置されるため、位置を手で調整する必要はありません（そもそも調整できません——配置はマニフェストの内容から機械的に決まります）。

- **枠色と下端バッジ** — 観測対象／ミラー集約先／観測外（死角）
- **破線の矢印** — 実際にミラーされるトラフィックの流れ
- **二重丸のノード** — 複数セグメントに接続する資産（ゲートウェイなど）。接続先へ線が伸びます
- **ホバー** — 資産のロール・IP・構造化対象などの詳細が出ます

> この図は**編集中のプレビュー**です。記事・資料・READMEに載せる確定版の図は `python platform/cli.py diagram <manifest>.yaml` で生成してください。

### 図の下：検証結果

| 印 | 意味 |
|---|---|
| ✕（エラー） | このままではYAMLとして出せません。出力ボタンも無効になります |
| ! （警告） | 宣言としては妥当ですが、**実際に環境を立ち上げた時に問題になります** |

警告は「宣言時には通るのに実行時に壊れる」類の落とし穴を先回りして伝えるものです。現在のところ次の2つを検出します。

- **ゲートウェイの静的IP不足** — 観測対象セグメントとミラー集約先のすべてに静的IPが無いと、ミラーリング設定の生成が失敗します
- **起動コマンド内の二重引用符** — 後述

### 右：YAML

常に最新の状態が出ています。エディタを使わずに手書きしたい場合の、書き方の参考にもなります。

## 書き出したあと

「YAMLをダウンロード」で保存します。ファイル名は `<name>.generated.yaml` になります。

保存したYAMLから環境を立ち上げるには、リポジトリを手元に用意して次を実行します。

```bash
git clone https://github.com/schutzz/ot-range-amenonuboco.git
cd ot-range-amenonuboco
pip install -r requirements.txt

python platform/cli.py provision <保存したファイル>.yaml
docker compose -f <保存したファイル>.docker-compose.yml up -d
```

ネットワーク図（外部依存のない自己完結HTML）も生成できます。

```bash
python platform/cli.py diagram <保存したファイル>.yaml
```

## 既存のマニフェストを読み込む

2つの経路があります。

**組み込みテンプレート（インストール不要）** — 右上のプルダウンから、15分野のリファレンス構成を選べます。いずれも実機で動作確認済みの構成なので、これを土台に自分の環境へ作り変えるのが最短です。

プルダウンは深さごとに3つの群に分かれています。**実演あり**（電力・上下水道・重要製造業）は攻撃・検知まで作り込んだ分野、**器のみ**（化学・商業施設・通信・ダム・食品農業・医療）はトポロジ・計装・構造化の3層のみ、**器のみ・観測境界あり**（原子力・輸送・緊急サービス・防衛産業基盤・政府施設・金融）は構造的に観測できない領域を死角として持つ分野です。どの分野が何をどこまでモデル化しているかは [分野カバレッジ](./sector-coverage.md) にまとめています。

> エディタが編集するのはトポロジ・計装・構造化の3層です。実演ありの分野を読み込んだ場合、検知・攻撃・可視化の層は取り込み時に落ちます（書き出したYAMLにも含まれません）。

**手元のマニフェスト** — YAMLを直接読み込む機能はありません。次のコマンドで変換してから、出力された `.gui.json` をエディタの画面へドラッグ＆ドロップしてください。

```bash
python platform/cli.py gui-export <manifest>.yaml
```

一手間に見えますが、これはブラウザ側にYAMLパーサを持ち込まないための設計です。変換に本体と同じ読み込み処理を使うので、**エディタが解釈する内容と実際にプロビジョナが解釈する内容がズレません**。

## つまずきやすいところ

### 無関係な Docker コンテナが動いていないか確認する

`docker compose up` する前に、ホスト上に本プロジェクトと無関係なコンテナ・ネットワークが動いていないか確認してください。可視化層（Grafana等）を持つ分野はホストポートを固定で公開するため、別のプロジェクトが同じポート（例: `3000`）を握っていると起動そのものに失敗します。無関係なコンテナが動いた状態での実機確認は、ミラーリング・構造化・検知の動作を保証しません。

### 起動コマンドに二重引用符を使わない

資産の `overrides.command` に書いた内容は、生成される `docker-compose.yml` の中で最終的に `sh -c "..."` の形で包まれます。**中に二重引用符があるとこの包みが破れ**、コンテナ内でシェルの構文エラーになります。

YAMLとしてもスキーマとしても妥当なので宣言時には弾けず、`docker compose up` して初めて壊れます。エディタは警告として指摘しますが、書き方としては**単一引用符を使ってください**。

```bash
# NG
python3 -c "print('hello')"

# OK
python3 -c 'print(1)'

# 引数として渡せば引用符自体を減らせる
python3 -c 'import sys;print(sys.argv[1])' hello
```

同じ理由で、バイナリデータを送りたい場合は `printf` のバックスラッシュエスケープ（`\x04` 等）も避けてください。Docker Compose の文字列解釈の層でバックスラッシュが失われます。base64 でエンコードした文字列を埋め込み、コンテナ内で `base64 -d` する方が確実です。

### コメントは保持されない

エディタの書き出しにコメントは含まれません。また、書き出しは**常に新しいファイル**（`<name>.generated.yaml`）で、読み込み元のファイルを上書きする機能はありません。

これは意図的な制限です。リポジトリの `manifests/*.yaml` は、なぜその構成にしたか・実機検証で何が分かったかといった経緯をコメントとして持っており、エディタの往復でそれらが失われる事故を構造的に防いでいます。

### 検知ロジック・攻撃・ダッシュボードは作れない

エディタが扱うのは `topology`（構成）・`instrumentation`（観測）・`structuring`（構造化）の3層までです。検知プラグイン・攻撃エンジン・可視化ダッシュボードの層は含みません。

これらはマニフェスト外のスクリプトやJSON定義として書く領域であり、プラットフォームは中身を一切解釈しない、という設計になっているためです。エディタで組み立てられるようにすると、この境界が曖昧になります。これら3層を使う場合は、書き出したYAMLに手で追記してください（書き方は [マニフェスト記法ガイド](./manifest-schema-guide.md) を参照）。

なお、3層だけでも**そのまま動作する有効なマニフェスト**が成立します（残りの層はすべて任意宣言です）。
